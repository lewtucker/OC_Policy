01 — The Problem

Issues with Running OpenClaw Uncontained

Default: "Yolo" Mode

  • ✕ Exec policy is security=full, ask=off out of the box
  • ✕ Agent can delete, overwrite, or exfiltrate files with zero prompts
  • ✕ Native file read/write tools run directly on the host — no sandbox
  • ✕ No rate limits, no time constraints, no identity awareness
  • ✕ A misconfigured or compromised agent has full access to everything the process can reach

What "Yolo" Looks Like

$ openclaw exec-policy show

Effective security:  full
Effective ask:        off
Ask fallback:         full

→ Any command. No approval. No log.

Available Presets

# Switch to cautious mode:
openclaw exec-policy preset cautious
# → asks before unknown commands

openclaw exec-policy preset deny-all
# → blocks all exec calls
02 — Container CLI

Running OpenClaw in a Container

The --container <name> flag runs the OpenClaw CLI itself inside an existing Docker/Podman container. This limits host-side file access — not just bash execution.

What IS Isolated

  • ✓ Filesystem outside bind mounts — invisible to the process
  • ✓ Process namespace — container sees only its own processes
  • ✓ Accidental damage — rm -rf / only nukes the container rootfs
  • ✓ Most kernel state — can't modify host system settings

What is NOT Isolated

  • ✕ Network — full internet and LAN access by default
  • ✕ Mounted directories — workspace dir is fully writable from inside
  • ✕ File read tools — native agent file reads still run on the host runtime
  • ✕ Container escape vulnerabilities — not a VM-grade boundary
"The container is a different computer in your house" — physically separate filesystem and processes, but still on your network with full internet access.
03 — Tool Sandbox

Running Agent Tool Calls in Containers

Key distinction: Containers in OpenClaw are for the tool sandbox, not the agent itself. The agent loop (LLM → parse → dispatch) runs as a normal Node process on the host.

How It Works

  • → Agent loop runs on host as a normal Node process
  • → Shell/bash tool calls → docker exec → openclaw-sbx-{session}
  • → Container runs sleep infinity, workspace dir bind-mounted
  • → Browser tools get their own container: openclaw-sbx-browser-*

Configure It

openclaw config set \
  agents.defaults.sandbox.backend docker

openclaw config set \
  agents.defaults.sandbox.docker.image \
  ghcr.io/openclaw/openclaw:latest

# Pull the image once:
docker pull ghcr.io/openclaw/openclaw:latest

What the Sandbox Isolates

  • ✓Filesystem outside workspace mount
  • ✓Process namespace
  • ✓Bash command execution
  • ✕Network access (still unrestricted)
  • ✕Mounted workspace directory
⚠ File read/write tools bypass the container entirely — they run on the host via the agent runtime. Even with sandbox.backend: docker, the agent can read any file the openclaw process can reach.
04 — Internet Access

Controlling What OpenClaw Can Reach

By default OpenClaw has unrestricted outbound internet access — any service, any API, any domain. Three practical layers of control, from lightweight to strict:

Approach 1 — HTTP_PROXY

  • 1Set HTTP_PROXY / HTTPS_PROXY at launch
  • 1Route through Squid, mitmproxy, or any filtering proxy
  • 1Works for any agent — zero code changes
  • ✕Bypassable if agent spawns subprocesses that ignore env

Approach 2 — Docker Network Rules

  • 2iptables rules on the Docker bridge: block all by default
  • 2Allowlist specific IPs / CIDR ranges
  • ✓Enforced at the kernel — agent cannot bypass
  • ✕IP-based only — no domain names, no content inspection

Approach 3 — Policy Proxy (ZPL / ZPR)

  • ✓Domain + URL allowlist/blocklist in plain language
  • ✓MCP tool-call inspection before forwarding
  • ✓Identity-aware — different rules per agent or role

Nanoclaw + OneCLI Integration

Nanoclaw now has OneCLI built in. Every agent container gets three capabilities automatically — no changes to OpenClaw or the agent itself.

  • ✓ Credential injection — secrets never appear in the agent's context or environment; OneCLI injects them at the transport layer
  • ✓ Access token injection — per-service tokens attached to outbound requests automatically (GitHub, Slack, etc.)
  • ✓ Proxy filtering — all outbound traffic routed through OneCLI's proxy; domains not on the allowlist are silently dropped

Example: nanoclaw config

# nanoclaw .env / container config
HTTP_PROXY=http://onecli:8080
HTTPS_PROXY=http://onecli:8080

# OneCLI allowlist
allow: api.anthropic.com
allow: api.github.com
allow: api.slack.com
deny:  *   # block everything else

# Credential injection (no secrets in agent ctx)
inject:
  api.github.com:
    header: Authorization: token {{GITHUB_TOKEN}}
  api.slack.com:
    header: Authorization: Bearer {{SLACK_TOKEN}}
05 — Egress Control

Controlling Where Agents Can Go

Place a ZPL proxy at the output of every agent. Any agent that supports HTTP_PROXY needs zero code changes.

Layer 1 — MCP Frame Inspection
  • →Reads structured tool calls (tool name, arguments)
  • →Evaluates against policy before forwarding to MCP server
  • →Blocks specific tools, time-of-day restrictions
Layer 2 — Downstream HTTP
  • →Intercepts all outbound HTTP from agents and MCP servers
  • →Evaluates destination, method, path against policy
  • →Catches curl, direct API calls, anything that bypasses MCP
Containerized bonus: Agent identity derived automatically from container IP — no tokens, no self-declaration.

ZPL Policy Examples

# Whitelist approved AI providers
Allow * to access api.anthropic.com
Allow * to access api.openai.com
Never allow * to access *.unauthorized-domain.com

# No automated runs outside staffed hours
Never allow openclaw to access opentrons-mcp
  with tool:run_protocol after 22:00
Never allow openclaw to access opentrons-mcp
  with tool:run_protocol before 07:00

# MCP servers shouldn't call external AI APIs
Never allow opentrons-mcp to access api.anthropic.com
Never allow opentrons-mcp to access api.openai.com

# Log every authorized run start
Allow openclaw with role:authorized-operator
  to access opentrons-mcp with tool:run_protocol,
  and signal "run-started" to AuditLog
